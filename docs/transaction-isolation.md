# 트랜잭션 전파 옵션 / 격리 수준별 이상 현상

## 트랜잭션 전파 옵션 (Propagation)

Spring `@Transactional`의 `propagation` 속성은 **이미 진행 중인 트랜잭션이 있을 때, 새로 호출된 메서드가 그 트랜잭션에 어떻게 합류할지**를 정한다. 실무에서 자주 쓰는 것은 `REQUIRED`, `REQUIRES_NEW`, `NESTED` 정도이고 나머지는 알아두는 수준으로 정리했다.

| 옵션 | 기존 트랜잭션이 있을 때 | 기존 트랜잭션이 없을 때 |
|---|---|---|
| `REQUIRED` (기본값) | 기존 트랜잭션에 참여(합류) | 새 트랜잭션 시작 |
| `REQUIRES_NEW` | 기존 트랜잭션을 잠시 보류하고 완전히 새로운(독립적인) 트랜잭션 시작 | 새 트랜잭션 시작 |
| `NESTED` | 기존 트랜잭션 안에 중첩 트랜잭션(세이브포인트) 생성 | 새 트랜잭션 시작 |
| `SUPPORTS` | 기존 트랜잭션에 참여 | 트랜잭션 없이 실행 |
| `NOT_SUPPORTED` | 기존 트랜잭션을 보류하고 트랜잭션 없이 실행 | 트랜잭션 없이 실행 |
| `MANDATORY` | 기존 트랜잭션에 참여 | 예외(`IllegalTransactionStateException`) 발생 |
| `NEVER` | 예외 발생 | 트랜잭션 없이 실행 |

- **`REQUIRED`**: 가장 많이 쓰는 기본값. 호출자에게 트랜잭션이 있으면 그대로 합류하기 때문에, 안쪽 메서드에서 예외가 나면 바깥 트랜잭션 전체가 롤백된다(하나의 물리 트랜잭션을 공유하므로).
- **`REQUIRES_NEW`**: 바깥 트랜잭션과 완전히 분리된 별도의 물리 트랜잭션을 커밋/롤백한다. 예를 들어 "주문은 실패해도, 로그는 반드시 남겨야 한다" 같은 경우 로그 저장 메서드를 `REQUIRES_NEW`로 두면, 주문 트랜잭션이 롤백돼도 로그 트랜잭션은 이미 커밋되어 남는다. 다만 커넥션을 하나 더 점유하므로 커넥션 풀 고갈에 주의해야 한다.
- **`NESTED`**: JDBC 세이브포인트(savepoint)를 이용해 바깥 트랜잭션 안에 중첩 트랜잭션을 만든다. 중첩 트랜잭션이 실패하면 그 지점까지만 롤백(세이브포인트로 복귀)하고, 바깥 트랜잭션은 계속 진행할 수 있다. `REQUIRES_NEW`와 달리 물리 트랜잭션은 하나뿐이고, 바깥 트랜잭션이 롤백되면 중첩 트랜잭션도 함께 롤백된다. (드라이버/DB의 세이브포인트 지원이 필요하고, JPA에서는 기본적으로 지원되지 않아 별도 설정이 필요하다.)
- **`MANDATORY`/`NEVER`**: "이 메서드는 반드시 트랜잭션 안에서만/밖에서만 호출돼야 한다"는 제약을 코드로 강제할 때 쓴다.

## 격리 수준 (Isolation Level)

트랜잭션 격리 수준은 **동시에 실행되는 여러 트랜잭션이 서로의 변경/조회에 얼마나 영향을 줄 수 있는지**를 정한다. 격리 수준을 낮출수록(느슨하게 할수록) 동시성(성능)은 좋아지지만 아래 이상 현상이 발생할 가능성이 커진다.

- **Dirty Read (더티 리드)**: 다른 트랜잭션이 아직 커밋하지 않은 변경 사항을 읽는 것. 그 트랜잭션이 이후 롤백하면, 내가 읽은 값은 애초에 존재한 적 없는 값이 된다.
- **Non-repeatable Read (반복 불가능한 읽기)**: 한 트랜잭션 안에서 같은 행(row)을 두 번 조회했는데, 그 사이 다른 트랜잭션이 그 행을 UPDATE하고 커밋해서 값이 달라져 있는 것.
- **Phantom Read (팬텀 리드)**: 한 트랜잭션 안에서 같은 조건으로 두 번 조회했는데, 그 사이 다른 트랜잭션이 조건에 맞는 행을 INSERT(또는 DELETE)하고 커밋해서 **행의 개수**가 달라져 있는 것. (Non-repeatable Read가 "같은 행의 값 변화"라면, Phantom Read는 "결과 집합에 새로 나타나거나 사라지는 행"이라는 차이가 있다.)

## 격리 수준별 이상 현상 비교표

| 격리 수준 | Dirty Read | Non-repeatable Read | Phantom Read | 비고 |
|---|:---:|:---:|:---:|---|
| `READ UNCOMMITTED` | 발생 가능 | 발생 가능 | 발생 가능 | 커밋 전 데이터도 읽을 수 있음. 실무에서 거의 쓰지 않음 |
| `READ COMMITTED` | 방지 | 발생 가능 | 발생 가능 | 커밋된 데이터만 읽음. **Oracle, PostgreSQL의 기본값** |
| `REPEATABLE READ` | 방지 | 방지 | (표준상) 발생 가능 | 트랜잭션 시작 시점 스냅샷 기준으로 반복 조회 시 같은 값 보장. **MySQL(InnoDB)의 기본값**이며, InnoDB는 갭 락(gap lock) 덕분에 Phantom Read까지도 실질적으로 방지 |
| `SERIALIZABLE` | 방지 | 방지 | 방지 | 트랜잭션을 순차 실행한 것과 같은 결과 보장. 동시성이 가장 떨어짐 |

- 격리 수준이 올라갈수록(`READ UNCOMMITTED` → `SERIALIZABLE`) 이상 현상은 줄어들지만, 락 경합이 늘어나 처리량(TPS)은 떨어지는 트레이드오프가 있다.
- Spring `@Transactional(isolation = Isolation.READ_COMMITTED)`처럼 지정할 수 있고, 기본값(`Isolation.DEFAULT`)은 데이터베이스 드라이버의 기본 격리 수준을 그대로 따른다 — 그래서 같은 코드라도 MySQL과 PostgreSQL에서 기본 격리 수준이 다를 수 있다는 점을 알고 있어야 한다.
- 이 프로젝트(H2)는 기본적으로 `READ COMMITTED`에 준하는 동작을 하며, 실습에서 별도로 격리 수준을 낮추거나 높추는 코드는 작성하지 않았다 — N+1/영속성 컨텍스트 실습과 격리 수준 실습을 분리하기 위해, 이번 주차 코드 제출 범위는 N+1 쪽으로 한정했다.
