# 영속성 컨텍스트: 1차 캐시 / 쓰기 지연 / 변경 감지

영속성 컨텍스트(Persistence Context)는 엔티티를 영구 저장하는 환경으로, `EntityManager`가 내부적으로 들고 있는 캐시이자 작업 공간이다. 아래 세 가지 동작이 모두 이 영속성 컨텍스트 위에서 이루어진다.

## 1차 캐시 (First-level Cache)

- 영속성 컨텍스트 내부에 있는 `Map<식별자, 엔티티>` 형태의 캐시. `EntityManager`(트랜잭션) 단위로 생성되고, 트랜잭션이 끝나면 함께 사라진다.
- `em.persist(entity)`로 저장하거나 `em.find()`로 조회한 엔티티는 1차 캐시에 올라간다.
- `em.find(Member.class, id)`를 호출하면:
  1. 먼저 1차 캐시에서 해당 식별자의 엔티티를 찾는다.
  2. 있으면 DB를 조회하지 않고 캐시에 있는 엔티티를 그대로 반환한다.
  3. 없으면 DB에서 조회한 뒤 결과를 1차 캐시에 저장하고 반환한다.
- 같은 트랜잭션 안에서 같은 식별자를 여러 번 조회해도 SQL이 한 번만 나가는 이유가 이것이다. 반대로 이 특성 때문에 N+1 재현 테스트를 작성할 때는 `em.clear()`로 1차 캐시를 강제로 비워야 한다 — 비우지 않으면 두 번째 조회부터는 쿼리 없이 캐시에서 반환되어 N+1이 드러나지 않는다.
- 1차 캐시는 동일성(identity)을 보장한다. 같은 트랜잭션 안에서 같은 식별자로 조회한 엔티티는 항상 `==` 비교가 참이다 (반복 가능한 읽기, REPEATABLE READ를 애플리케이션 레벨에서 흉내 낸다고 볼 수 있다).

## 쓰기 지연 (Transactional Write-Behind)

- `em.persist(entity)`를 호출해도 INSERT SQL이 즉시 나가지 않는다. 대신 영속성 컨텍스트 내부의 **쓰기 지연 SQL 저장소(SQL 저장 큐)**에 SQL을 등록만 해두고, 트랜잭션을 커밋하는 시점(정확히는 flush 시점)에 모아서 DB로 보낸다.
- 이렇게 지연시키는 이유는 JDBC 배치(batch)를 활용하기 위해서다. 여러 건의 INSERT/UPDATE/DELETE를 모아뒀다가 한 번에 DB로 전송하면, 트랜잭션 커밋 직전에 모아 보내는 쪽이 매번 즉시 보내는 것보다 네트워크 왕복 횟수를 줄일 수 있다.
- flush가 일어나는 시점: `em.flush()` 직접 호출, 트랜잭션 커밋 직전, JPQL 쿼리 실행 직전(플러시 모드가 AUTO인 경우 — 방금 등록한 변경사항이 JPQL 조회 결과에 반영되도록 먼저 내보낸다).
- flush는 "커밋"이 아니다. flush는 쓰기 지연 SQL 저장소의 SQL을 DB로 보내는 것뿐이고, 실제 DB 트랜잭션을 확정 짓는 커밋과는 별개다. flush 이후에도 롤백하면 반영된 내용은 사라진다.

## 변경 감지 (Dirty Checking)

- 영속 상태의 엔티티를 수정하면(`setter` 호출 등) `em.persist()`나 별도의 `update()` 호출 없이도 변경 사항이 자동으로 DB에 반영된다. 이 매커니즘이 변경 감지다.
- 동작 방식:
  1. 엔티티가 영속성 컨텍스트에 처음 들어올 때(조회/저장 시점), 그 상태를 그대로 복사한 **스냅샷**을 함께 보관한다.
  2. flush 시점에 영속성 컨텍스트는 관리 중인 모든 엔티티를 스냅샷과 비교한다.
  3. 값이 달라진 필드가 있으면 UPDATE SQL을 쓰기 지연 SQL 저장소에 등록한다.
  4. 이 UPDATE는 기본적으로 **엔티티의 모든 컬럼을 갱신**한다(엔티티 단위로 미리 만들어둔 UPDATE 문을 재사용할 수 있어 성능에 유리하고, 매핑도 예측 가능하기 때문). 컬럼 수가 많거나 매핑된 테이블이 많은 경우에는 `@DynamicUpdate`로 실제로 변경된 컬럼만 UPDATE하도록 바꿀 수 있다.
- 변경 감지는 **영속 상태의 엔티티에만** 적용된다. 준영속(detached)이나 비영속(transient) 엔티티를 수정해도 아무 일도 일어나지 않는다 — 이 경우엔 `em.merge()`로 다시 영속 상태로 만들어야 한다.
- 삭제(`em.remove()`)나 신규 저장(`em.persist()`)은 변경 감지 대상이 아니라 즉시 쓰기 지연 SQL 저장소에 등록된다.

## 세 동작의 관계

```
em.persist(order);              // ① INSERT SQL이 쓰기 지연 저장소에 등록됨 (아직 DB 반영 X)
order.setStatus(CANCELED);      // ② 영속 상태 엔티티 수정 → flush 시 변경 감지 대상

// ... 트랜잭션 커밋 시점 (또는 em.flush() 호출 시점) ...
// ③ 변경 감지로 UPDATE SQL이 쓰기 지연 저장소에 추가 등록됨
// ④ 쓰기 지연 저장소에 쌓인 SQL(INSERT, UPDATE ...)이 DB로 flush됨
// ⑤ 트랜잭션 커밋
```

- `em.persist()`로 저장한 엔티티는 즉시 1차 캐시에 올라가고(조회 시 재사용 가능), 실제 INSERT는 쓰기 지연 저장소를 거쳐 flush 시점에 나간다.
- 그 엔티티를 이후에 수정하면, 별도 저장 호출 없이 변경 감지가 flush 시점에 UPDATE를 만들어준다.
- 셋 다 "트랜잭션이 끝나기 전까지는 실제 DB 상태와 애플리케이션 메모리 상태가 다를 수 있다"는 전제를 깔고, 그 차이를 flush 시점에 한꺼번에 동기화한다는 공통점이 있다.
